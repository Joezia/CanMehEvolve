# 后续实验说明(给回来后阅读)

这些实验都是在已提交的冻结结果之外做的补充,**没有改动 `runs/deepseek/` 等已提交目录**,结果都在 `runs/followup/`。全部作业结束后会自动生成 `runs/followup/SUMMARY.md`(汇总表)和 `SUMMARY.json`;如果没有,运行 `python3 scripts/followup/aggregate_followup.py`。作业提交记录在 `runs/followup/submission.txt`。`smoke-*` 和 `null-search-smoke-*` 是小规模冒烟测试,不属于结果。

## 任务 1:把 greedy 种子 3、4、5 补到 40 次请求(`resume-greedy-s*`)
种子 3、4、5 当时只发了 38、34、34 次请求就碰到 3 小时作业上限。这里沿用种子 1 的做法:重放保存的随机抽取、恢复保存的最佳补丁,只补发缺的请求,然后对最终补丁再独立测 3 次。看 `SUMMARY.md` 的第 1 节:补发了几次请求、有没有新的更新、最终加速比变化。注意:续跑发生在另一个节点上。

## 任务 2:规则在真实 SDK 上的误报率(`sdk-inert-*`)
Phase 0 的误报率是在人造负载上测的(0/100,上限 3.6%)。真实 SDK 的计时可能更重尾、相邻重复可能相关,所以要在真实 SDK 上再测一次:用一个"什么都不改"的补丁(真实比例恰好 1.000),用和正式运行完全相同的测量与判定规则重复测很多次。只要规则判"更快",就是一次误报。两类节点(xcnc/xcnd)各测 120 次。看第 2 节的"judged faster"(误报次数)和置信区间。

## 任务 3:空搜索(`null-search-*`)——贪心排序规则会不会被噪声推着走
贪心的更新规则只要求 R(两次测量中较差的一次)低于当前记录,没有 2% 门槛,也没有显著性检验。Phase 0 校准的是最后的判定规则,并没有校准这个排序规则。这里把模型换成"只加一行注释"的无效改动(编译结果完全不变,真实比例恰好 1.0),照样跑 36 步贪心循环,看记录会因噪声下降多少、更新几次。如果噪声就能让记录下降 0.3%,那么真实贪心链里小于 0.3% 的步骤就不能当作真实改进。看第 3 节:updates 和 final record。

## 任务 4:补丁正确性(`correctness-diff-*`、`correctness-sanitize-*`)
目前只有 harness 的校验和检查。这里加两类检查,对象是 10 个最终补丁和种子 3 链的 11 个中间状态:
- 4a 差分测试:生成约 400 个 FIT 文件(4 个原文件加上改动字节并重算 CRC 的变异文件),分别用原库和打了补丁的库解码,比较输出摘要。不一致就是补丁改变了行为;两个库在同一个恶意输入上同时崩溃不算差异。
- 4b 消毒器:用 AddressSanitizer+UBSan 编译(查内存错误和未定义行为),用 ThreadSanitizer 在 4 个线程同时解码(查数据竞争,比如惰性建表没有加锁)。原库作为对照应当没有告警。
看第 4 节。只要某个补丁出现差异或告警,它就不能被称为"正确"。

## 任务 6:best-of-N 的叠加对照(`stack-bestofn-*`)
greedy 比 best-of-N 高,可能只是因为 greedy 能把多个函数的独立收益叠加起来,而 best-of-N 只保留一个。这里不再调用模型:取 best-of-N 同一次运行里已经生成的候选,每个函数选最好的一个,按单独收益排序,逐个叠加成 1、2、3…个函数的累计补丁,每个都用冻结的测量方法独立测 3 次。如果叠加几个后 best-of-N 追上 greedy,说明差距主要来自"保留并叠加",而不是 greedy 找到了更好的改写。看第 6 节:每个种子的 K 与加速比。
